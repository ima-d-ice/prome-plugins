## Phase 9 — Chunking milestone (DONE)

- `chunkers/contracts/`: shared `Chunk`/`BlockReference` models (unique deterministic ids,
  doc_id = `ParsedDocument.source`, page/block provenance with sub-block char ranges),
  runtime-checkable `Chunker` protocol, `ChunkerError`/`ChunkerConfigError`, config
  validation (`validate_size_overlap`), counters (`CharacterCounter` honest default,
  `ApproxTokenCounter` heuristic, `CallableCounter` wrapping any `str -> int`),
  `flatten_document()` canonical flattening (blocks in reading order joined by blank
  lines; each block carries `[start, end)` offsets) and `build_chunks()` shared assembly.
- `chunkers/fixed/` FixedSizeChunker: char windows + word-boundary snapping (and rewind-
  forward snapping after overlap), tokenizer mode packs word atoms re-measuring overlap,
  best-effort size limit, deterministic, empty docs → [].
- `chunkers/recursive/` RecursiveChunker: separator hierarchy (`\n\n`, `\n`, `. `, ... `""`
  hard cut) + greedy left-to-right packing with trailing-atom overlap carry. NOT
  parent/child chunking (flat list out).
- `chunkers/structure_aware/` StructureAwareChunker: pending-heading glue (headings never
  orphaned from following content), major-section boundary closes (same-or-higher level;
  unleveled headings treated as level 1), blocks atomic unless oversized (oversized blocks
  split by recursive separators, pieces packed), heading_path/heading_level/block_types
  metadata, page/block provenance.
- No mandatory dependencies; stdlib only. No hierarchical/semantic/code/table/spreadsheet/
  email/proposition/LLM chunkers (out of milestone scope).
- Token counting is pluggable (`tokenizer=`); counts are labeled (`length_unit`:
  characters / approx_tokens / tokens) and never passed off as exact model tokens.
- Readmes: `chunkers/README.md` (shared contract, install, quick start, comparison) +
  `chunkers/{fixed,recursive,structure_aware}/README.md`; benchmark methodology in
  `benchmarks/chunkers/README.md`; root `README.md` gained a Chunkers section; wheel/sdist
  include `chunkers*`.
- Benchmark: `benchmarks/chunkers/benchmark.py` (15 fixtures, same parser fixtures,
  performance and quality reported separately, no combined score, archive of previous
  reports, `sections-boundary violation rate` structure metric). Reports in
  `benchmarks/chunkers/reports/`. Boundary preservation on this corpus: fixed ~100% loss,
  recursive ~98%, structure-aware 0%; coverage 1.0 everywhere.
- Tests: `tests/chunkers/` (contracts, per-chunker suites, integration over real PDF/HTML/
  DOCX/PPTX/XLSX/CSV fixtures incl. unicode + determinism + provenance).

## Phase 10 — Chunking milestone 2: hierarchical + semantic (DONE)

Adds exactly two strategies; the chunking module now holds **five** strategies
(fixed, recursive, structure_aware, hierarchical, semantic). No other strategy was
introduced; the three earlier chunkers are untouched and still pass unchanged.

- `chunkers/hierarchical/` HierarchicalChunker: one-level parent/child chunking.
  - Parents come from the **structure-aware** chunker at `parent_size` (so parents
    respect major section boundaries and carry heading context); children are carved out
    of each parent with the **shared recursive splitter** at `child_size` /
    `child_overlap`. No splitting logic duplicated.
  - Config: `parent_size` (2000), `child_size` (500), `child_overlap` (50), `tokenizer`.
    Validated: child_size <= parent_size, overlap < child_size.
  - Output is `HierarchicalResult` (`.parents`, `.children`, `.parent_of()`,
    `.children_of()`, `.as_dict()`), NOT a flat list — documented.
  - Links are bidirectional in metadata: child → `parent_id`/`parent_index`/
    `child_index`; parent → `child_ids`/`child_count`. No orphaned children, no parent
    without children (guaranteed by construction).
  - Stable ids: `<digest>-hierarchical-parent-NNNN` / `<digest>-hierarchical-child-NNNN`.
  - `chunk_children()` returns the flat child list for vector-store use; `iter_pairs()`
    yields (parent, children).
- `chunkers/semantic/` SemanticChunker: meaning-aware boundaries from a **pluggable,
  injected** embedding model. Never loads a model, never hardcodes a provider, never
  falls back to another strategy when inference fails (raises `SemanticChunkerError`).
  - Uses the shared `embeddings.contracts` interface: candidate segments are wrapped in
    `EmbeddingInput` and sent through `embed_documents()`; the `dense_vector` of the
    returned `EmbeddingResult` drives the cosine comparison.
  - **Threshold interpretation (documented):** `similarity_threshold` is the *minimum
    adjacent cosine similarity*; a similarity **below** it marks a topic change and a
    chunk boundary. Range [-1, 1], default 0.5. Recorded in metadata as
    `semantic_threshold_kind="minimum_adjacent_cosine_similarity"`.
  - Config: `embedding_model` (required), `similarity_threshold`, `max_chunk_size`,
    `min_chunk_size` (optional), `overlap`, `tokenizer`, `batch_size`,
    `respect_structure`.
  - Structure: headings open a chunk and are glued to their content; sections are never
    merged just because embeddings look similar; lists/tables/code kept atomic (split on
    row boundaries only if oversized); no content discarded; block refs accurate.
  - Headings are NOT compared by similarity (a title's embedding says nothing about
    topical coherence).
  - Validation: dense-only (sparse/multi-vector rejected), dimension consistency,
    `EmbeddingResult.dimensions` cross-check, missing dense vector, wrong result count,
    non-finite values, missing model, model without `embed_documents`.
  - Metadata records `embedding_model`, `embedding_dimension` and a `semantic_config`
    snapshot for reproducibility.
- Embedding contracts (delivered in parallel with this milestone, shared with the
  embeddings ecosystem): `embeddings/contracts/{models,protocols}.py` are the
  authoritative contract; this milestone added `embeddings/deterministic.py`
  (dependency-free hashed bag-of-words model for tests/benchmarks) and
  `embeddings/local/transformers_model.py` (offline adapter for a locally cached
  transformer checkpoint, never downloads weights).
- Tests: `tests/chunkers/test_hierarchical.py` (39) and `tests/chunkers/test_semantic.py`
  (53) — all with deterministic fake embedding models, no weight downloads.
- Benchmark extended to five strategies: parent/child counts, orphan and link-consistency
  metrics, embedding inference time and batch throughput, hierarchy-aware size
  distribution. Semantic runs on the deterministic fake model by default
  (`--semantic-embedding fake`); `--semantic-embedding local` uses the cached
  all-MiniLM-L6-v2 checkpoint (optional, never downloads). Reports archived before
  overwrite.
- Docs: `chunkers/hierarchical/README.md`, `chunkers/semantic/README.md`, updated
  `chunkers/README.md` (five-strategy table, parent-child vs semantic comparison,
  limitations) and `benchmarks/chunkers/README.md` (new metric groups).
- Packaging: `embeddings*` added to the wheel/sdist package list; `MANIFEST.in` added so

### Technical notes (milestone 2)

- The embeddings contract was delivered concurrently into `embeddings/` while this
  milestone was in progress. The semantic chunker was rewritten against the delivered
  contract (`embed_documents(list[EmbeddingInput]) -> list[EmbeddingResult]`), not against
  a locally invented one; `embeddings/contracts/{models,protocols}.py` are treated as
  authoritative and are not modified by this milestone.
- `embeddings/qwen3` had a module-level `from sentence_transformers import
  SentenceTransformer`, which broke `import embeddings` (and therefore the chunker) when
  the optional dependency is absent. Fixed to match the lazy pattern already used by
  `bge_m3`/`coderank` — the adapter is now importable without sentence-transformers and
  raises only on actual use.
- The semantic chunker deliberately keeps its own cosine-similarity helper instead of
  importing `embeddings.contracts.validation`, so it depends only on the stable
  `embeddings.contracts.models` module.
- `build_chunks` trims whitespace at span edges, so consecutive chunks are separated by
  a single whitespace character rather than being strictly contiguous. This is shared
  behaviour across all chunkers and is what the coverage metric is computed against.
- The deterministic fake embedding model is a hashed bag-of-words projection: it is
  reproducible and dependency-free, but it is NOT a semantic model and is only used for
  tests and algorithm benchmarks.

## Phase 11 — Vector store ecosystem milestone (DONE)

- `vector_stores/contracts/`: backend-independent contracts
  - `models.py`: CollectionConfig, VectorSpaceConfig, StoredRecord, SpaceVectors,
    ChunkProvenance, SearchRequest, SearchResult, CollectionInfo, ScrollPage
  - `filters.py`: portable metadata filter language (eq/ne/in/not-in/gt/gte/lt/lte/
    exists + and/or/not) with `validate_filter`
  - `indexes.py`: IndexKind, IndexConfig/IndexDescription, HnswIndexConfig,
    SparseIndexConfig, PayloadIndexSpec/PayloadFieldType, IndexKindCapability
  - `capabilities.py`: StoreCapabilities (discoverable per-backend capabilities)
  - `protocols.py`: the `VectorStore` protocol + `iter_records`/`collect_records`
  - `validation.py`: the portable rules (config, record, search request)
  - `exceptions.py`: VectorStoreError hierarchy
- `vector_stores/qdrant/`: first adapter (Qdrant)
  - `store.py`: QdrantVectorStore (memory / local / server modes), QdrantStoreConfig
  - `mapping.py`: point-id mapping, payload encoding/decoding, filter translation
  - `_client.py`: lazy `qdrant-client` import
- Reused contracts, nothing duplicated: `chunkers.contracts.models.Chunk` /
  `BlockReference` for the stored chunk, `embeddings.contracts.models.
  EmbeddingSpaceDescriptor` for the embedding-space identity,
  `RepresentationType` for the vector kinds, `Normalization` for the normalization.

Key decisions:
- A collection declares one or more NAMED vector spaces; each space pins the vector
  kind, the width, the distance metric and the embedding space (model + revision).
- Compatibility = model id + revision + width + normalization + representation kind.
  Matching dimensions alone are NOT sufficient (reused from the embedding ecosystem).
- One named space holds exactly one representation kind: a dense space never receives
  a sparse vector, a multi-vector space never receives an averaged vector.
- Qdrant point ids are UUIDs; the chunk id (`{digest}-{strategy}-{index}`) is mapped to
  a deterministic UUIDv5 and the ORIGINAL id is preserved in the payload.
- Payload layout: user metadata at the top level (filterable/indexable), contract
  fields under the reserved `_prome` key, `chunk_id`/`doc_id` promoted.
- The declared collection configuration is stored in the collection metadata, so the
  "foreign model" check still applies after a restart.

Index capabilities:
- Priority 1 (exact): `params={"exact": True}` - baseline for the recall measurement.
- Priority 2 (HNSW): `HnswIndexConfig(m, ef_construct, full_scan_threshold)` at
  collection creation, `params={"hnsw_ef": ...}` at query time. Defaults are
  conservative (m=16, ef_construct=100).
- Priority 3 (sparse inverted): Qdrant indexes sparse vectors natively;
  `SparseIndexConfig(full_scan_threshold=...)`.
- Priority 4 (payload): only the fields the user declares are indexed
  (`PayloadIndexSpec`), keyword/integer/float/boolean/datetime.
- Priority 5 (multi-vector): Qdrant `max_sim` comparator over the token matrix.
- Deferred: IVF, PQ, scalar/binary quantization, custom ANN, BM25/full-text.

- Qdrant server 1.20.0 was started locally (podman) to verify the server-only paths

## Phase 13 — Retrieval: hierarchical (coarse-to-fine) retrieval (DONE)

Adds the retrieval ecosystem and its first strategy. IMPORTANT: the Phase 1
retrieval milestone described in the task brief (shared retrieval contracts,
dense retriever, BM25, RRF, hybrid, indexing coordination, deduplication,
adjacent merging) was **not present in this repository** — the tree contained
only `parsers/`, `chunkers/`, `embeddings/` and `vector_stores/`, and the root
README still stated "No retrieval ... nothing consumes them yet". The shared
foundation the hierarchical strategy needs was therefore built here, and the
shared result contract was designed so that a later hybrid/BM25/RRF milestone
can plug into it without changing the callers. BM25, RRF and the hybrid
strategy were deliberately NOT implemented (the brief puts them out of scope
for this milestone).

- `retrieval/contracts/`: the shared result contract —
  `RetrievalResult` (evidence + optional context), `RetrievalContext` /
  `ContextChunk`, `RetrievalResponse`, `RetrievalDiagnostics` and the
  `RetrievalStrategy` protocol. The evidence (the matched chunk) and the
  context (parent section, neighbours) are separate fields, so a caller can
  never confuse them.
- `retrieval/dense/`: `DenseRetriever` — embeds the query with the *injected*
  model and runs a filtered vector search. It checks the backend's
  `StoreCapabilities` **before** searching (unsupported filter operations and
  undeclared fields on fixed-schema backends raise
  `UnsupportedRetrievalCapabilityError`), verifies that the model and the
  collection share an embedding space, and applies the score threshold itself
  so the meaning of a threshold does not depend on the backend.
- `retrieval/strategies/hierarchical/`:
  - `HierarchicalIndexer` — embeds parents and children **independently** with
    the same encoder and writes both into the same collection and the same
    named dense vector space. Idempotent (re-indexing replaces), preserves the
    chunk ids, the relationship and the provenance, and refuses to link a
    parent and a child of different documents. The relationship is written
    into the record metadata (`parent_id` on a child, `child_ids` /
    `child_count` on a parent), so it survives a restart of the store.
  - `ParentStage` — the coarse stage. Searches only `chunk_level == "parent"`.
  - `ChildStage` — the fine stage. Searches only
    `chunk_level == "child" AND parent_id IN (selected parents)`, so the
    restriction is applied by the backend and never widened silently.
  - `HierarchicalRetrievalStrategy` — runs the two stages in order, embeds the
    query **once**, deduplicates, expands the context and produces the
    standardized results.
- `retrieval/postprocessing/context_expansion/`: attaches the parent section
  and, optionally, the neighbouring children of the same parent. It never
  rewrites or summarizes the source text, never repeats a chunk and never
  crosses the parent boundary.
- The hierarchy metadata contract (`metadata.py`) projects the relationship
  the hierarchical chunker already writes into the chunk metadata
  (`level`, `parent_id`, `child_ids`, `child_count`, `child_index`) into the
  filterable record metadata. The chunker's algorithm and its metadata were
  **not** modified.
- `embeddings/deterministic.py` was **restored**: it is documented in the root
  README, in `chunkers/README.md` and in `chunkers/semantic/README.md` and it
  is imported by `benchmarks/chunkers/benchmark.py`, but the module was
  missing from the tree, which broke that benchmark. It is a dependency-free
  hashed bag-of-words double for tests and algorithm benchmarks — not a
  production encoder and not a semantic model.

Test results:
- `pytest tests/retrieval` — **65 passed** (parent stage, child stage, the
  full strategy, context expansion, persistence, edge cases) plus **2 passed**
  with the real Qwen3-Embedding-0.6B weights (`test_integration_qwen.py`).
  The Qwen integration test skips cleanly when `sentence-transformers` or the
  weights are absent.
- `pytest tests/chunkers tests/embeddings tests/retrieval` — **566 passed**.
- `pytest tests/vector_stores` (without faiss) — **192 passed, 63 skipped**
  (the skips are the server-only tests; no Qdrant server is reachable here).
- `pytest tests/vector_stores/faiss` (on its own) — **57 passed, 1 skipped**.
- `pytest tests/parsers` — **337 passed, 5 skipped**.
- No pre-existing test was changed or removed.

Evaluation (labeled corpus of 3 documents / 16 parents / 44 children /
13 queries, `benchmarks/retrieval/hierarchical/evaluate.py`):
- With the **real Qwen3** encoder: `flat` R@1 0.731 / R@5 0.923 / MRR 0.897 /
  nDCG@10 0.901; `parent` R@1 0.846 / R@5 1.000 / MRR 0.949 / nDCG@10 0.962;
  `hierarchical` R@1 0.731 / R@5 0.923 / MRR 0.897 / nDCG@10 0.901 — i.e. the
  hierarchy **matched** the flat search on the evidence metrics while the
  fine stage scored **54.2 %** fewer candidates. The coarse stage alone was
  the best system on this corpus, which is reported as measured.
- With the deterministic double: flat and hierarchical again agree exactly
  (R@1 0.577 / R@5 0.769 / MRR 0.777), with 46.0 % fewer candidates. The
  deterministic model is lexical, so these numbers describe the architecture,
  not the semantic quality of an encoder.

Benchmark (deterministic synthetic corpus, 100 documents / 12 600 records,
Qdrant in-memory, 100 queries): indexing 1 666 records/s; query latency
p50/p95 — flat 59.4/62.1 ms, parent 58.8/61.6 ms, hierarchical 192.6/214.0 ms;
candidate reduction 99.8 % of the child records. The hierarchical strategy
performs **two** filtered scans where the flat search performs one, and the
in-process Qdrant modes evaluate a payload filter with a full scan, so the
latency is roughly doubled. This is a property of those modes, not of the
strategy; it is reported as measured.

## Phase 14 — Retrieval: hybrid engine (DONE)

Adds the hybrid retrieval engine: dense semantic retrieval (Qwen3-Embedding-0.6B)
fused with BM25 lexical retrieval (SQLite FTS5) through Reciprocal Rank Fusion.

- `retrieval/contracts/`: extended. Adds `RetrievalQuery`, `RetrievedItem`
  (canonical name; `RetrievalResult` kept as a backwards-compatible alias),
  `RetrievalResponse` (ordered results, query, strategy, diagnostics, timings),
  `Retriever` (canonical protocol name; `RetrievalStrategy` kept as an alias),
  `RetrievalCapabilities`. `RetrievalDiagnostics` now records per-channel
  candidate counts, channel failures and the fused score scale.
- `retrieval/dense/qwen/`: `QwenDenseRetriever` — the production dense
  channel. It binds the generic dense retriever to the Qwen encoder, validates
  that the injected model matches the collection's embedding space, and checks
  the backend's filter capabilities before searching.
- `retrieval/lexical/bm25/sqlite_fts5/`: the BM25 channel. The index is a
  relational content table plus an FTS5 virtual table kept in sync by SQLite
  triggers (external content mode). The FTS5 tokenizer is `unicode61` with
  `tokenchars '_'`, so identifiers such as `get_user_id` survive as one token.
  The index is persistent, supports upsert/delete/delete-by-document, a MATCH
  expression built from the query, metadata filtering through the same AST as
  the dense channel (translated to SQL with bound parameters), and an integrity
  check that covers every content row.
- `retrieval/fusion/rrf/`: Reciprocal Rank Fusion, default `k=60`. Only ranks
  are used, so the dense and BM25 score scales are never compared. Per-channel
  ranks and scores are recorded; the tie-break is deterministic (score desc,
  then chunk id asc). Channel weights are supported.
- `retrieval/postprocessing/deduplication/`: keeps one entry per chunk id,
  preserves the channel that found it, keeps the best-ranked occurrence.
- `retrieval/postprocessing/adjacent_merge/`: optional merge of consecutive
  chunks of the same document. Configurable size limit; never crosses the
  document boundary; preserves the evidence reference and the contributing
  chunk ids.
- `retrieval/indexing/coordinator.py`: writes the same chunks into both indexes.
  Reports per-backend success and failure (`partial`); offers
  `reconcile_lexical()` to retry the lexical side after a failure. Never loads
  an embedding model itself.
- `retrieval/strategies/hybrid/`: the orchestration. Strict by default — a
  failing channel makes the whole retrieval fail. `"partial"` policy available
  explicitly.
- `embeddings/deterministic.py`: unchanged from Phase 13.

Test results:
- `pytest tests/retrieval` — **190 passed** (contracts, dense, BM25, RRF,
  dedup, adjacent merge, hybrid strategy, indexing coordinator, integration
  with the real Qwen3 encoder, FTS5 index). Two Qwen integration tests pass
  when sentence-transformers and the cached weights are usable; otherwise they
  skip.
- `pytest tests/` — **1220 passed, 68 skipped**.
- `pytest tests/vector_stores/faiss` (isolated) — **57 passed, 1 skipped**.

Evaluation (`benchmarks/retrieval/hybrid/evaluate.py`):
- Real Qwen3-Embedding-0.6B, 18 queries over 9 chunks:
  - dense: 0.833 R@1 / 0.889 R@3 / 1.000 R@5 / 1.000 R@10 / MRR 0.880
  - bm25: 0.444 R@1 / 0.444 R@3 / 0.444 R@5 / 0.444 R@10 / MRR 0.444
  - hybrid: **1.000 on every metric** / MRR 1.000
- The deterministic double (hashed bag-of-words) gives dense and hybrid the
  same scores (0.722 R@1 / 0.889 R@3 / 1.000 R@10 / MRR 0.821), because the
  double is itself lexical.
- The corpus is 3 documents and 18 queries: the numbers are suggestive, not
  statistically significant. The hybrid win with Qwen is consistent with the
  per-query breakdown (dense nails the paraphrase queries, BM25 nails the
  exact-identifier queries, hybrid gets all of them).

Benchmark (synthetic corpus, Qdrant memory, 50/100/200 documents):
- indexing throughput: ~6 900 records/s
- query latency p50/p95 — dense 0.69/0.84 ms, bm25 0.09/0.17 ms,
  hybrid 0.79/0.94 ms (50 documents); scales linearly with the corpus size.
